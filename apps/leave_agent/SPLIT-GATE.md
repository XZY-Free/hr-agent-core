# 请假Agent未来拆分门禁

请假流程包含多轮槽位、用户确认、权限与身份校验、排班和余额读取，以及请假单JSON生成。任一跨Runtime边界处理不完整都会造成串会话、重复提交或错误员工数据，因此本阶段保持在Orchestrator本地。

## 会话门禁

- 多轮槽位必须有持久化Schema和版本策略。
- Runtime重启后能够恢复未完成的请假会话。
- 多实例并发读取同一会话时必须保持一致。
- 不同`user_id/session_id`之间不得读取或覆盖对方状态。
- 超时、取消和会话不存在必须有明确错误语义。

## 身份门禁

- A2A请求必须携带可验证的员工身份上下文和调用方身份。
- Runtime API Key只用于服务认证，不得冒充员工身份。
- `client_secret`、AK/SK、JWT、模型Key和Runtime API Key不得进入A2A消息。
- 员工、租户和会话三者的绑定关系必须由服务端校验。

## 幂等与交易门禁

- 每次请假确认必须具有稳定幂等键和业务请求ID。
- 网络超时或重试不得生成两份请假单或重复提交。
- 权限、性别、排班、余额、天数校验顺序保持冻结。
- 校验使用的数据版本和最终请假单必须可关联审计。
- 继续保持“智能体生成请假单JSON、业务后端负责提交”的业务结论。

## 恢复与观测门禁

- Orchestrator与Leave Runtime之间传递统一request ID和Trace上下文。
- 提供超时、鉴权失败、Runtime不可用、500和非法响应的失败注入。
- Runtime重启、下游部分失败和回滚必须能够恢复到明确状态。
- 日志和Trace不得记录请假事由正文、凭据或完整员工敏感信息。

## 拆分验收

只有会话持久化、身份、幂等、恢复、失败注入和跨Runtime Trace全部通过后，才允许创建独立Leave Runtime。未满足前不得通过本地/A2A双轨或复制实现绕过门禁。

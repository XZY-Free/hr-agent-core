# WP-02 请假状态模型与确定性规则引擎整改

## 1. 目标

把当前 Leave 从：

```text
LLM 直接拼 type/date/time/leave_days
        ↓
submit_leave 做若干校验
```

整改为：

```text
自然语言
  ↓
Leave Agent 理解用户意图
  ↓
显式 Leave Draft（带字段来源）
  ↓
确定性标准化
  ↓
确定性排班/权限/性别/余额/时间/时长/连续性校验
  ↓
权威 Leave Form
  ↓
用户确认
  ↓
现有提交/输出边界
```

本专题**不处理最终业务动作 JSON 的假实现问题**，但必须保证“送到最终边界之前”的 Leave Form 是可靠的。

---

## 2. 第一原则：建立显式 Leave Draft

当前多轮请假主要依靠模型聊天历史，这不足以承载交易状态。

必须建立 session-scoped 的 `LeaveDraft` 概念。

它不是重新做 FastGPT 全局变量，而是一个**单一业务草稿对象**。

---

## 3. Leave Draft 必备字段

以下是必须表达的业务语义，不要求照抄 Python 类名，但不能缺失。

### 3.1 草稿标识

- draft_id
- revision
- status

status 至少区分：

- collecting
- ready_for_validation
- validation_failed
- ready_for_confirmation
- confirmed
- terminal

### 3.2 假期类型

- raw_type_expression
- normalized_type_name
- type_code
- source

标准化必须由确定性规则完成：

```text
年假 -> 年休假
调休 -> 调休假
```

typeCode 必须来自 `HOLIDAY_TYPE_CODE`，不能由模型记忆。

### 3.3 日期

保留两层。

#### 用户请求层

- requested_date_expression
- requested_date_segments

`requested_date_segments` 用来表达：

- 单个日期；
- 日期范围；
- 用户明确列出的离散日期。

不得过早把：

```text
10号、11号、15号
```

压成：

```text
10号到15号
```

否则无法校验“中间有工作日断裂”。

#### 权威层

- authoritative_start_date
- authoritative_end_date

来源只能是：

- normalized_user；
- schedule；
- rule。

### 3.4 时间表达

必须区分：

- full_day
- first_half
- second_half
- explicit_range
- explicit_hours

保留：

- requested_start_time
- requested_end_time
- requested_hours
- authoritative_start_time
- authoritative_end_time

不能只保存一个 float `leave_days`。

### 3.5 时长

必须改为：

```text
duration_value
duration_unit
```

unit 至少：

- day
- hour

权威时长：

- authoritative_duration_value
- authoritative_duration_unit

原因：

旧 Gaia 余额本身有 `leaveUnit`；

“提前1小时下班”“调休2小时”不能强制换成 0.5 天。

### 3.6 理由

- reason
- reason_source

允许：

- 用户明确说 -> `user`
- 用户没说 -> 空

禁止：

```text
用户没说 -> 自动填“个人事务”
```

本轮不新增“所有假都必须填理由”的业务规则。

如果后续真实后端明确要求某类假强制理由，应在领域规则中另配，不得现在擅自推断。

### 3.7 字段来源 provenance

每个交易字段至少能判断来源：

- user
- normalized_user
- schedule
- rule
- system

**模型生成但无法追溯来源的值，不允许进入权威表单。**

## 4. Draft 修改的依赖失效规则

这是多轮智能体区别于工作流硬节点的关键。

用户修改一个字段时，要失效所有依赖它的计算结果。

### 4.1 修改假期类型

例如：

> “改成病假。”

必须失效：

- type_code
- permission validation
- gender validation
- balance validation
- rest-day mode
- duration-unit compatibility
- 已生成确认摘要

日期原值可保留，但必须重新按新假种验证。

### 4.2 修改日期

例如：

> “改到后天。”

必须失效：

- authoritative start/end date
- schedule facts
- half-day boundaries
- night-shift correction
- duration derived from schedule
- rest-day validation
- balance validation
- confirmation

### 4.3 修改时间

例如：

> “结束时间改成16:00。”

必须失效：

- authoritative duration
- balance validation
- cross-day correction
- confirmation

### 4.4 修改理由

只失效：

- reason
- confirmation

不得重新查排班、余额。

---

## 5. 假期类型规则

现有 `SKIP_RESTDAY_MAP` 作为业务资产继续保留。

### 5.1 连续自然日类

当前已确认：

- 婚假
- 产假
- 病假
- 育儿假
- 计划生育假
- 无薪产假
- 有薪产假
- 子女护理假
- 不定时员工日常休假
- 产前假
- 陪产假
- 出差
- 公出

语义：

> 这些假期以连续自然日计算，休息日可以包含在假期范围内。

因此：

**不得因为首日排班是 OFF 就直接返回 rest_day。**

### 5.2 跳过休息日类

当前已确认：

- 丧假
- 产检假
- 非独生子女护理假
- 事假
- 调休假
- 无薪侍产假
- 80%病假
- 调休假(综合工时)
- 有薪侍产假
- 年休假
- 无薪假
- 路程假
- 全薪病假
- 哺乳假

语义：

> 权威天数由有效排班工作日计算。

## 6. 休息日规则整改

当前 `submit_leave` 在知道类型规则之前就：

```text
start_time == 00:00 -> rest_day
```

必须删除这种全局语义。

### 6.1 连续自然日假

如果请求：

> 周六开始请产假

且周六为休息日：

- 不因休息日拒绝；
- 日期仍是周六；
- 继续按连续自然日计算。

如果后台表单必须有日内时间，而休息日没有班次：

- 使用**集中定义的 calendar-day canonical time**；
- 当前迁移业务基线使用 `08:00 - 18:00`；
- 该值必须是领域常量，不得由 Prompt 或模型决定；
- 不得伪造为 Gaia 排班时间，来源标记为 `rule`。

### 6.2 跳休类——单个明确休息日

用户明确：

> “周六请一天年假。”

且周六是休息日：

返回 rest_day：

> 该日期是正常休息日，不需要请年休假。

不得自动把申请移动到周一。

### 6.3 跳休类——持续时长请求

用户说：

> “从周六开始请2天年假。”

如果周六是休息日：

- requested start 仍记录周六；
- authoritative start 为周六之后第一个已知工作日；
- 从 authoritative start 开始累计两个已知工作日；
- 如果没有足够排班证据，不得把未知日期算成工作日。

---

## 7. 排班模型必须从二态改成三态

领域规则必须明确：

```text
WORK
REST
UNKNOWN
```

当前：

```text
None -> not True -> 当工作日
```

必须彻底取消。

### 7.1 WORK

有明确排班记录，且 shift_code 不是休息班次。

### 7.2 REST

有明确排班记录，并满足：

- OFF
- off_day
- defaultOFF 前缀
- 其他现有统一休息班次判断。

### 7.3 UNKNOWN

包括：

- 目标日期不在返回数据中；
- Gaia 返回缺日期；
- 排班响应为空；
- 解析失败；
- 查询范围之外。

UNKNOWN 不得：

- 当 WORK；
- 当 REST；
- 自动使用系统周一到周五；
- 自动使用国家法定工作日。

---

## 8. 排班查询范围必须由规则引擎决定

当前做法：

```text
get_schedule(start_date, end_date)
```

之后直接计算。

这对跳休不够。

### 8.1 跳休计算

领域服务应按“需要多少个有效工作日”驱动排班拉取。

必须支持：

1. 从 requested start 开始查询；
2. 如果当前窗口内工作日不足，继续向后扩窗口；
3. 每批范围受 Gaia 接口约束；
4. 直到：
   - 找够目标工作日；
   - 或达到安全上限；
   - 或 Gaia 明确无法提供后续排班。

不得：

- 查询不到后续日期就把后续当工作日。

### 8.2 安全上限

本轮统一：

- 单次 Leave 规则搜索最长不超过 366 个自然日；
- 超过后返回明确 `schedule_horizon_exceeded`；
- 不使用旧代码的 27 天特殊分支。

---

## 9. 删除 `>27 天 -> shrink_workday` 业务语义

`>27` 是旧工作流在固定排班窗口下的技术处理，不是 HR 业务规则。

整改后：

### 连续自然日假

无论 1 天、27 天、98 天：

```text
end = start + requested calendar duration
```

按统一规则。

### 跳休假

无论 1 天、30 天：

按实际已知工作日计数。

不得：

```text
days > 27 -> end 直接取排班列表最后一个工作日
```

当前 `calc_end_date` 的 `shrink_workday` 相关语义退休；不要保留一套新规则之外的兼容分支。

---

## 10. 时长权威计算

这是本专题最重要的交易规则。

模型提供的 `leave_days` / `hours` 只能是用户意图解释，不是最终事实。

### 10.1 全天

权威时段：

- 工作日：取实际 shift start / shift end；
- 连续自然日遇休息日：取 canonical calendar-day time。

### 10.2 上半天 / 上午 / 前半天

权威时段：

```text
shift start -> meal begin / first-half boundary
```

### 10.3 下半天 / 下午 / 后半天

权威时段：

```text
meal end / second-half boundary -> shift end
```

### 10.4 0.5 天但未明确上/下午

保持旧业务语义：

> 默认第一半天。

即：

```text
first_half
```

但由领域规则设置，不写在多个 Prompt 里。

### 10.5 明确 N 小时

例如：

- 提前1小时下班；
- 上班晚到2小时并调休；
- 下午调休1.5小时。

必须保持：

```text
duration_unit = hour
```

不得先强制换为：

```text
0.5天
```

### 10.6 小时与余额单位

Gaia 假期余额必须保留 leave unit。

比较余额时：

- 小时余额只与小时请求比较；
- 天余额只与天请求比较；
- 如果后台明确存在单位换算标准，未来另建规则；
- 本轮没有规则证据，不得自行按“8小时=1天”硬转。

---

## 11. 排班适配必须保留半天边界原始数据

当前 `get_schedule` 只映射：

- shift_date
- shift_code
- shift_name
- start_time
- end_time

整改后如果 Gaia 原始响应存在：

- mealBeginTime
- mealEndTime
- middleTime
- 或等价字段

必须纳入统一 Schedule DTO。

不得丢掉后再由模型猜。

如果真实返回根本没有半天边界：

- 不得计算时间中点；
- 返回稳定 `schedule_detail_insufficient`；
- Agent 告知暂时无法确定半天排班边界。

---

## 12. 夜班跨日

现有：

```text
start_time > end_time -> end_date + 1
```

这个思路保留，但只能在已经得到**权威班次时段**后执行。

必须测试：

- 19:00 -> 次日07:00；
- 上半夜/下半夜；
- 多日夜班；
- 修改时间后重新计算。

不能只比较字符串来源不明的用户输入。

---

## 13. 多假种冲突

旧业务高优先级规则保留：

> 一次申请只能包含一个假期类型。

例如：

- “两天年假加一天调休”
- “病假或者年假都行”

进入同一请假申请时必须拒绝一次性合并，并提示分开办理。

检测责任：

```text
Leave Draft normalization
```

不能只靠 Prompt 提醒。

---

## 14. 离散日期连续性

旧业务定义：

> “不连续”的核心是中间存在未申请的工作日。

### 合法例子

> 周五和下周一请假

中间周六、周日均为休息日：

视为业务连续。

### 非法例子

> 10号、11号、15号请假

如果 12-14 日包含工作日：

视为不连续申请，提示拆开办理。

### 实现要求

1. 保留用户离散日期 segments；
2. 查询 gap 中的排班；
3. gap 只有 REST -> 可合并；
4. gap 出现 WORK -> `discontinuous_workday_gap`；
5. gap 出现 UNKNOWN -> 不得武断判连续，返回 `schedule_unknown_for_continuity`。

---

## 15. 权限、性别、排班、时长、余额的固定顺序

最终校验顺序：

1. type normalization；
2. permission；
3. gender；
4. date/continuity；
5. schedule evidence；
6. authoritative time/duration；
7. balance；
8. ready_for_confirmation。

当前 `submit_leave` 在权威 duration 计算前就比较余额，必须调整。

余额必须使用：

```text
authoritative_duration
```

而不是 LLM 原始值。

---

## 16. 理由字段

删除 Prompt 中：

> 用户不说则填“个人事务”。

新规则：

- 用户明确说 -> 原意保留；
- 用户没说 -> 空；
- 不改写成更“专业”的理由；
- 不把假种词当理由；
- 不把模型解释文本写入理由。

如果用户后续说：

> “理由改成去医院复诊。”

只更新理由字段，不影响日期/排班。

---

## 17. 结构化缺槽位状态

禁止继续用：

```text
模型回答有没有？
+
是否出现“日期/假期类型/事由”
```

判断 `input_required`。

### 17.1 Leave Draft 自己计算 missing fields

例如：

```text
missing = [type_name, date]
```

状态直接为：

```text
collecting
```

公共 Runtime 映射为：

```text
input_required
```

### 17.2 不允许自然语言决定系统状态

下面两句话都只是展示文案：

> “请问你想请哪种假？”

> “还需要假期类型。”

它们不能成为 status Authority。

## 18. 用户确认

当且仅当：

- 类型已标准化；
- 日期已确定；
- 时间/时长已确定；
- 权限通过；
- 性别通过；
- 排班证据完整；
- 余额通过；
- 日期连续性通过；

草稿才进入：

```text
ready_for_confirmation
```

展示给用户的是**权威字段**。

用户确认后再进入现有最终提交边界。

本轮不整改最终业务动作 JSON。

## 21. 单元测试矩阵

### 假种标准化

- 年假 -> 年休假
- 调休 -> 调休假
- 年休假保持
- 未知假种拒绝
- 两个不同假种 -> conflict

### 连续自然日

- 周六开始产假 -> 允许
- 周日开始病假 -> 允许
- 98 天产假 -> 不触发 27 天特殊逻辑
- 连续假跨多个休息日 -> 日期连续

### 跳休

- 周六单日年休假 -> rest_day
- 周六开始2天年休假 -> 从首个已知工作日计2个
- 周五开始2天年休假，周末休 -> 周五+周一
- 排班只查到周五，后续未知 -> 不得把周六/周日/周一当工作日
- 扩展查询后才完成日期

### 时长

- 全天
- 上午
- 下午
- bare 0.5 day -> first_half
- 1.5 day
- 提前1小时
- 调休2小时
- 1.5小时
- 天余额与小时请求 -> unit mismatch
- 小时余额与天请求 -> unit mismatch

### 夜班

- 19:00 -> 07:00
- 23:00 -> 00:00
- 夜班半天边界
- 修改日期后重新取夜班

### 连续性

- 周五+周一，周末休 -> 合法
- 10/11/15，中间工作日 -> 不连续
- 中间排班未知 -> 不允许自行判连续

### 权限/性别/余额

- 无权限
- 性别不匹配
- 余额不足
- 余额未知
- 单位未知
- 权威时长与用户声称时长不一致 -> 以领域结果为准并重新确认

### 理由

- 未提供 -> 空
- 提供 -> 保留
- 修改理由 -> 不重新查排班

### 多轮

- 缺类型+日期 -> structured input_required
- 补类型 -> 仍缺日期
- 补日期 -> 进入校验
- 修改日期 -> dependent facts invalidated
- 修改类型 -> permission/balance invalidated
- 用户问一句带“？”的普通问题 -> 不得误判 input_required

# 实施顺序、依赖与文件变更矩阵

## 1. 执行原则

实施 AI 必须严格按此表推进。

不允许：

- “先把容易的做了”；
- 一次横跨所有 WP 大改；
- 先改 Prompt 再补领域规则；
- 一边整改一边重写全部架构。

---

## 2. Phase 0：建立基线

只做：

1. 记录当前 commit；
2. 运行当前测试；
3. 记录当前 fail/skip；
4. 不修改代码。

输出基线信息即可，不要先修 unrelated failure。

## 11. 每个 Phase 的最小交付

每个 Phase 完成后必须：

1. 运行该 WP 文档指定测试；
2. 运行全量 unit；
3. `git diff --check`；
4. 搜索敏感字段泄露；
5. 输出变更文件列表；
6. 输出未完成项；
7. 未完成项非空时，不得写“完成”。

---

## 12. 禁止的跨 Phase 行为

### WP-01

不能顺手改 Leave 时长。

### WP-02

不能顺手做 page_jump business JSON。

### WP-03

不能把 Policy RAG 搬到 Employee Data。

### WP-04

不能让 Consult 查 employee_id。

### WP-05

不能删除 A2A contract validation。

### WP-06

不能改 SnowHarness。

### WP-07

不能为了测试通过而降低规则、skip case、改期望到当前错误行为。

---

## 13. 默认 Git 行为

除非上层用户另有明确要求：

- 不创建远端分支；
- 不 push；
- 不改远端 Runtime；
- 不写云端配置；
- 可以在本地工作树修改并测试；
- 是否 commit 由上层指令决定，默认不主动 commit。

---

## 14. 最终变更完成后必须执行

至少：

```text
uv sync --locked
uv run pytest -q
uv run pytest -q tests/eval/test_eval.py -m eval
uv run pytest -q tests/eval/test_consult_eval.py -m consult_eval
uv run pytest -q tests/eval/test_employee_data_eval.py -m employee_data_eval
```

以及新建的：

- production-topology suite
- routing semantic suite
- leave business golden suite
- attendance golden suite

具体新测试文件名由实现落地决定，但 README 中必须给出完整可运行命令。

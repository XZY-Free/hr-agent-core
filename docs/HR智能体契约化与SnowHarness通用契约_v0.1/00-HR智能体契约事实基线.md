# 00 — HR 智能体公共契约事实基线

> 审计仓库：`XZY-Free/hr-agent-core`
>
> 审计提交：`1f628f1b7bc99b4451d90f2cf2636fe66a9cfa6b`
>
> 本文只冻结当前真实代码事实，不把目标设计伪装成现状。

---

# 一、审计目的

本轮只回答：

1. 当前真正面向员工的 HR 智能体是谁；
2. 它现在实际具备哪些业务能力；
3. 当前内部已经存在什么协议和请求合同；
4. 哪些能力已经通过真实测试证明；
5. 哪些能力只是代码存在但尚未证明；
6. 哪些内部实现绝不能暴露成 SnowHarness 的公共合同；
7. 为后续顶层公共契约改造提供唯一事实基线。

---

# 二、当前顶层业务入口

当前业务结构：

```text
hr-orchestrator
├─ 本地 leave_agent
├─ 本地 page_jump
├─ 本地取消引导
├─ 本地人工入口
├─ A2A → hr-consult-agent
└─ A2A → hr-employee-data-agent
```

证据：

- `README.md`
- `apps/orchestrator/README.md`
- `agent.py`

当前 `hr-orchestrator` 是员工入口。

但是它当前由：

```text
AgentkitAgentServerApp
```

承载。

这里的智能体开发套件服务（`AgentkitAgentServerApp`，负责把根智能体暴露成 AgentKit 服务）不是本轮要交给 SnowHarness 的长期公共协议。

当前 Orchestrator：

```text
http://127.0.0.1:8000
```

有自身服务入口，但没有顶层标准 A2A 智能体卡片。

因此当前事实为：

```text
Consult：
已是独立 A2A Provider

Employee Data：
已是独立 A2A Provider

HR Orchestrator：
是总业务入口
但不是顶层 A2A Provider
```

这就是本轮最核心的缺口。

---

# 三、SnowHarness 应看到的对象

SnowHarness 以后只应知道：

```text
企业人力智能助手
```

不应知道：

```text
root_agent
leave_agent
hr-consult-agent
hr-employee-data-agent
page_jump
DeterministicA2AMiddleware
OrchestratorRemoteRouter
veADK
AgentKit
```

这些全部属于 HR 智能体内部实现。

公共边界必须是：

```text
SnowHarness
    ↓
企业人力智能助手公共契约
    ↓
顶层 A2A Provider
    ↓
HR Orchestrator
    ↓
内部 Leave / Consult / Employee Data
```

---

# 四、当前业务能力事实

当前 Orchestrator 路由与评测实际覆盖：

- 请假申请与修改；
- 请假多轮信息补充；
- 本人假期余额；
- 医疗期；
- 工龄与年假折算；
- 人力制度咨询；
- 考勤制度咨询；
- 薪酬福利咨询；
- 人力系统操作指导；
- 人力文档问答；
- 页面跳转；
- 取消请假引导；
- 人工服务；
- 闲聊。

公共能力不应把每个 Tool 或内部路由变成一条能力。

第一版建议收敛为四个业务能力域：

```text
1. 假勤与请假服务
2. 员工本人信息服务
3. 人力制度与福利咨询
4. 人力系统与文档协助
```

页面跳转、人工入口、取消页面引导暂不直接作为通用智能体能力。

原因：

```text
[[JUMP:xxx]]
```

属于当前宿主产品动作协议，不是可移植的通用 Agent 能力。

后续如 SnowHarness 建立正式“宿主动作合同”，再纳入公共契约。

---

# 五、现有能力声明已经具备正确粒度

咨询智能体的智能体卡片（`AgentCard`，A2A 对外公开智能体身份、协议与能力的标准描述）当前声明：

- 人力制度咨询；
- 人力福利咨询；
- 人力系统操作指导；
- 人力文档问答。

员工数据智能体当前声明：

- 员工本人假期余额查询；
- 员工本人医疗期查询；
- 员工本人年假计算。

这些能力是“任务领域”，不是函数方法。

这是正确方向，应作为通用规范的样板。

# 六、当前内部 A2A 请求合同

共享请求对象：

```text
A2ARequestContext
```

当前强制字段：

```text
request_id
user_id
session_id
caller_agent
locale
message
context_summary
```

当前内部规则还要求：

```text
caller_agent = hr_orchestrator
locale = zh-CN
```

并对元数据字段做严格允许列表检查。

这是一份：

```text
HR Orchestrator
→ 内部 Consult / Employee Data
```

的私有合同。

它不能直接作为：

```text
SnowHarness
→ 企业人力智能助手
```

的公共合同。

尤其禁止 SnowHarness 伪造：

```text
caller_agent = hr_orchestrator
```

---

# 七、身份事实

员工数据智能体已经存在服务端可信身份映射：

```text
A2A user_id
→ TrustedIdentityResolver
→ employee_id
→ employee_ref
```

其中：

- `employee_id` 不直接暴露；
- 对外结果使用不可逆 `employee_ref`；
- 未验证身份返回稳定 `identity_unverified`；
- A2A `user_id` 明确禁止直接当作业务 `employee_id`。

这是正确安全边界。

顶层公共合同应进一步收敛为：

```text
SnowHarness 执行主体
（ExecutionSubject，SnowHarness 本次执行所代表的可信调用者身份）
        ↓
HR Agent
        ↓
内部身份映射
        ↓
employee_id
```

SnowHarness 不应理解或传入：

```text
employee_id
corp_id
Gaia JWT
client_secret
```

---

# 八、敏感信息边界

当前共享 A2A 请求过滤器明确拒绝：

- 客户端密钥；
- 授权头；
- Bearer 令牌；
- Runtime API Key；
- Gaia JWT；
- AK/SK；
- employee_id；
- target_employee_id；
- corp_id。

这是当前公共契约应继续保留的正确原则：

> 平台只传身份主体和允许的业务上下文，不传 HR 内部凭据、企业内部业务主键和底层系统密钥。

---

# 九、会话连续性事实

当前 Orchestrator：

```text
ShortTermMemory(backend="local")
```

按：

```text
user_id
session_id
```

维持会话。

内部 A2A 调用：

```text
context_id = session_id
```

因此当前 Agent 已经有连续会话语义。

但是当前 A2A 服务端任务存储仍属于进程内任务存储。

因此必须区分：

```text
会话连续性：
已有基础

跨进程/重启后的任务持久恢复：
当前未证明
```

公共契约不得把“有 contextId/taskId”直接宣传成“支持可靠持久恢复”。

---

# 十、流式事实

当前咨询与员工数据智能体的智能体卡片声明：

```text
streaming = true
```

真实 A2A 网络测试已经证明：

- 可以建立流式事件通道；
- 可以收到 Artifact 更新事件；
- 可以收到任务状态更新事件；
- 最终任务进入完成状态。

但当前执行器主要流程仍然是：

```text
业务运行完成
→ 形成完整结果
→ 添加 Artifact
→ 完成
```

因此：

```text
流式传输：
已证明

逐 Token / 连续内容增量生成：
未证明
```

公共契约必须把这两个能力分开。

---

# 十一、等待用户补充事实

咨询智能体已经存在：

```text
need_more_information
→ input-required
```

这里的等待用户补充（`input-required`，A2A 表示任务因缺少用户业务信息而暂停等待输入的状态）已经有真实协议基础。

请假智能体本身也明确支持：

- 缺一项自然追问一项；
- 缺多项时一次说明；
- 提交前统一确认。

因此顶层 HR Agent 很适合把所有真正缺失业务信息统一转换成：

```text
input-required
```

再由 SnowHarness 恢复原任务。

---

# 十二、恢复事实

内部系统已经有多轮会话语义。

但是目前没有证据证明顶层：

```text
同一个 A2A taskId
+
同一个 contextId
+
input-required
+
下一次输入恢复原任务
```

已经完整实现。

因此：

```text
多轮业务：
已有

顶层 A2A 原任务恢复：
待实现
```

---

# 十三、取消事实

咨询与员工数据执行器都已经存在 A2A `cancel()` 处理。

但当前没有足够证据证明：

```text
取消请求
→ 中断正在运行的模型/工具
→ 不再产生成功结果
→ 最终稳定为 cancelled
```

因此只能冻结：

```text
取消处理入口：
存在

真实底层取消级联：
未证明
```

未来公共契约只有 Contract Test 证明成功后，才能声明强取消支持。

# 十五、认证事实

当前 A2A 客户端将 Runtime API Key 放在：

```text
Authorization: Bearer ...
```

HTTP Header 中。

不进入：

- A2A Message；
- Context；
- Artifact；
- 普通日志。

这是正确方向。

顶层 HR Agent 与 SnowHarness 之间也必须保持：

```text
运行时认证
≠
智能体调用上下文
```

# 十七、本轮事实结论

当前项目不是“缺 A2A”。

真正缺的是：

```text
整个 HR 智能体
作为一个统一黑盒 Agent
对外提供完整公共合同
```

后续改造的中心必须是：

```text
顶层 HR Orchestrator
→ 公共 Agent Contract
→ 顶层 A2A Provider
```

而不是继续把 SnowHarness 接到内部 Consult / Employee Data。
